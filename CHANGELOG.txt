v3.30.5 (2026-05-16) — FIX: Bust de caché Docker + npm install en run.sh
────────────────────────────────────────────────────────────────────────────────

BUG: HA reutilizaba el layer Docker de npm install aunque package.json
hubiera cambiado (node-cron añadido en v3.30.4). Resultado: node-cron
seguía sin instalarse en el contenedor aunque el código lo requiriera.

FIX doble:
  1. Dockerfile: ARG VERSION=X.Y.Z incluido en la línea RUN npm install.
     Al cambiar la versión, Docker no puede cachear ese layer.
  2. run.sh: antes de lanzar node server.js, comprueba si node-cron existe.
     Si no, ejecuta npm install --production. Safety net para casos extremos.

v3.30.4 (2026-05-16) — FIX: node-cron no declarado + scheduleTask resiliente
────────────────────────────────────────────────────────────────────────────────

🚨 BUG: scheduleTask() hacía require('node-cron') pero el paquete NO
estaba declarado en package.json. Al ejecutarse el primer setTimeout
de scheduled tasks (~weekly-dashboard-review), el require fallaba y
tiraba el proceso entero. Esto se sumaba al problema de agent_network.

Además el try/catch existente NO protegía el require — estaba fuera.

FIX en 2 frentes:
  1. Añadido "node-cron": "^3.0.3" a package.json (la dep correcta).
  2. Movido const cron = require('node-cron') DENTRO del try, así si
     por alguna razón npm install no lo instalase, caemos al fallback
     con setInterval en vez de crashear.

VERIFICACIÓN: cross-check de TODOS los require() externos vs deps:
  cors, express, form-data, js-yaml, node-cron, node-edge-tts,
  node-fetch, ws → todos en package.json ✓
  child_process, crypto, dgram, fs, net, path → built-ins de Node ✓
  multer declarado pero sin require activo (extra dep, no rompe)

v3.30.3 (2026-05-16) — HARDENING: arranque resiliente ante módulos faltantes
────────────────────────────────────────────────────────────────────────────────

DEFENSIVE: El require de agent_network ahora va envuelto en try/catch.
Si el módulo falta por cualquier motivo (build incompleto, cache Docker,
archivo no commiteado), Jarvis arranca igualmente con un stub silencioso
y simplemente registra:
    [boot] agent_network no disponible (MODULE_NOT_FOUND: ...).
    Jarvis arranca SIN red de agentes.

Antes este caso provocaba un CRASH LOOP del contenedor entero
(falla require → server.js sale → s6 reinicia → falla otra vez...).
Ahora Jarvis es robusto frente a deployments parciales.

REGLA NUEVA: Cualquier módulo background opcional debe envolverse así.
Si en v3.31+ añadimos otro background_module nuevo, mismo patrón.
