================================================================================
VISIÓN GENERAL
================================================================================

Jarvis NO es un chatbot con un prompt gigante.
Es un sistema de 5 IAs especializadas + un router inteligente que decide
en tiempo real qué cerebro responde a cada mensaje.

Antes (monolito):  1 IA + prompt de 5000 tokens → lenta y cara
Ahora (NEXUS):     5 IAs + router → experto correcto + ~65% menos tokens

================================================================================
CAPA 1 — NEXUS ROUTER (0 tokens, instantáneo)
================================================================================

Cuando llega un mensaje, el router lo clasifica en 3 sub-capas:

SUB-CAPA 1.1: Regex (0 tokens, 0ms)
─────────────────────────────────────
Cubre ~70% de los mensajes. Si hay match, dispatch inmediato.

  "emergencia|urgente|fallo crítico"        → experto: emergencia
  "crea|modifica|github|server.js"          → experto: dev
  "automatización|dashboard|lovelace"       → experto: automatizacion
  "no funciona|error|caído|unavailable"     → experto: diagnostico
  "alexa|música|volumen|spotify"            → experto: multimedia
  "pvpc|consumo|kwh|precio luz"             → experto: energia
  "cámara|frigate|alarma|movimiento"        → experto: seguridad
  "proxmox|docker|vpn|nas"                  → experto: red
  "recuerda|aprende|memoria|qué sabes"      → experto: aprendizaje
  "investiga|analiza|compara|resume"        → experto: analisis
  "razona|análisis profundo|r1"             → experto: razonamiento
  "hola|ok|gracias" (< 30 chars)            → experto: rapido
  "enciende|apaga|temperatura" (< 80 chars) → experto: rapido

SUB-CAPA 1.2: Keywords de expertos dinámicos (0 tokens)
────────────────────────────────────────────────────────
Los expertos creados con nexus_manage pueden tener keywords propias.
Se comprueban aquí antes de pasar al LLM.

SUB-CAPA 1.3: LLM barato (gpt-4o-mini, ~10 tokens de output)
──────────────────────────────────────────────────────────────
Si ninguna regex encaja, se hace una llamada ultrabarata:
  System: "Clasifica en UNA palabra: rapido|ha_control|diagnostico|..."
  User:   [primeros 300 chars del mensaje]
  Output: "diagnostico"  (una sola palabra)

Fallback final: ha_control (si el LLM falla o devuelve nombre inválido)

================================================================================
CAPA 2 — ENSAMBLADO DEL SYSTEM PROMPT (L0-L4)
================================================================================

Cada experto recibe un system prompt construido dinámicamente en 5 capas.
Solo se incluye lo relevante para ese experto → menos tokens, mejor foco.

  L0: Base inamovible (~800 tokens)
  ───────────────────────────────────
  Identidad de Jarvis, filosofía, reglas de seguridad, formato de respuesta.
  Igual para TODOS los expertos. Se cachea con cache_control ephemeral.

  L1: Módulos del experto (~1500 tokens)
  ───────────────────────────────────────
  Cada experto tiene una lista de módulos activos. Solo se inyectan esos.
  Ejemplo (experto diagnostico): base + perseverance + diagnostico + ha_internals
  Ejemplo (experto dev): base + dev + filesystem + web + autonomy

  Módulos disponibles (20 total):
    base, philosophy, perseverance, autonomy, ha_control, ha_internals,
    diagnostico, automation, filesystem, web, network, proxmox, emergency,
    dev, inamovible, multimedia, energia, seguridad_casa, red_infra, aprendizaje

  L2: Contexto dinámico actual (~400 tokens)
  ────────────────────────────────────────────
  Se construye en cada request con datos reales de HA:
    - Presencia: quién está en casa
    - Luces encendidas / apagadas
    - Temperatura de cada zona
    - Dispositivos media en reproducción
    - Alertas activas

  L3: Contexto en vivo (~200 tokens)
  ────────────────────────────────────
  Estado justo antes del mensaje del usuario (si hay liveContext activo).
  Se actualiza cada 60 segundos en background.

  L4: Catálogo de tools del experto (variable)
  ─────────────────────────────────────────────
  Cada experto tiene una lista blanca de tools permitidas.
  Solo ve las tools que necesita → menos tokens, menos confusión del modelo.

  Ejemplo de reducción:
    rapido:       11 tools de 67 totales  (↓84%)
    ha_control:   24 tools de 67 totales  (↓64%)
    dev:          24 tools de 67 totales  (↓64%)
    razonamiento:  0 tools               (R1 no soporta function calling)

  Total prompt típico: 2000-3500 tokens vs 5000+ del monolito original.

  ───────────────────────────────────────────────────────────────

                     (maxTokens: 16000 para respuestas largas)

================================================================================
CAPA 4 — BUCLE AGÉNTICO (agentic loop)
================================================================================

Por cada turno de conversación:

  1. IA recibe: mensaje + system prompt (L0-L4) + historial + tools
  2. IA decide qué tools ejecutar (puede ser 0, 1 o N)
  3. Jarvis ejecuta TODAS las tools del turno en PARALELO (Promise.all)
  4. Resultados → historial como tool_results
  5. IA decide: ¿más tools o respuesta final?
  6. Repite hasta respuesta final o máximo 15 iteraciones

  Ejemplo real — "¿Por qué falla el clima del salón?":
    Iter 1: get_entity_state(climate.salon) + get_error_log()   [paralelo]
    Iter 2: get_history(climate.salon, 24h) + web_search(...)   [paralelo]
    Iter 3: Respuesta con diagnóstico completo

  Optimizaciones:
    · Tools en paralelo → más rápido
    · Resultados truncados a 8000 chars (2000 en saver mode) → menos tokens
    · Errores de tools → auto-registrados como learnings
    · SSE streaming → el usuario ve cada paso en tiempo real

================================================================================
CAPA 5 — MEMORIA PERSISTENTE (aprende entre sesiones)
================================================================================

  /data/memory.json          → Notas y preferencias del usuario
                               Cap: 500 notas (FIFO, elimina las más antiguas)

  /data/learnings.json       → Errores y soluciones aprendidas
                               Cap: 200 learnings

  /data/knowledge_db/        → Documentación HA estudiada
                               bootLearnHA: 20 páginas de developers.home-assistant.io
                               3 páginas por arranque, cada 6h hasta completar

  /data/history.json         → Historial de conversaciones

  /data/nexus/
    health.json              → Health scores por experto (0-100)
                               +2 por éxito, -8 por corrección del usuario
                               Si score < 20 → fallback a ha_control
    dynamic_experts.json     → Expertos creados con nexus_manage
    dynamic_modules.json     → Módulos custom creados en runtime

  Background jobs:
    Cada 30s   → checkEmergencies + nexusWatchers
    Cada 60s   → updateLiveContext (estado de la casa)
    Cada 10min → captureStateSnapshot (para análisis de patrones)
    Cada 30min → proactiveThinkingLoop (detecta anomalías)
    Cada 4h    → knowledgeExpansionLoop (estudia más documentación HA)
    Cada 6h    → analyzePatterns + distillLearnings
    Cada 12h   → checkSystemUpdates
    Al boot    → bootLearnHA (3 docs) + bootLearnOwnProject

================================================================================
CAPA 6 — GetawayAgentes (red de agentes IA)
================================================================================

Jarvis está conectado a una red de agentes IA externos.

  URL:       https://getaway-gateway.alejandra-app.workers.dev
  Protocolo: WebSocket persistente con exponential backoff reconnect
  Activado:  por defecto (AGENT_NET_ENABLED=true)
  Admin:     Adrián (padilla585projects)

  Cuando llega una tarea de la red:
    1. System prompt especial: prohibido compartir entidades/estados/paths HA
    2. Responde solo con conocimientos generales (domótica, HA, etc.)
    3. Nunca expone datos privados de la instalación

FLUJO COMPLETO — EJEMPLO
================================================================================

  Usuario escribe: "Jarvis, investiga por qué el sensor de temperatura del
                   baño lleva 3h sin actualizar"

  1. ROUTER (0 tokens):
     "investiga" → regex match → experto: analisis

  2. ENSAMBLADO (L0-L4):
     Módulos: base + autonomy + aprendizaje + optimization
     Modelo:  deepseek-chat (V3)
     Tools:   web_search, get_entity_state, get_history, knowledge_db...

  3. BUCLE AGÉNTICO:
     Iter 1: get_entity_state(sensor.temp_bano) + get_history(bano, 3h)
     Iter 2: web_search("HA sensor unavailable zigbee2mqtt causa")
     Iter 3: Respuesta con análisis + recomendaciones

  4. APRENDIZAJE:
     Si encuentra solución → learn() registra el patrón automáticamente
