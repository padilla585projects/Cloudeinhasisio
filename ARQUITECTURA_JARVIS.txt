1. QUÉ ES JARVIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Jarvis NO es un chatbot. Es un agente IA autónomo especializado en:
- Control domótico total (Home Assistant)
- Automatización industrial (PLCs, SCADA, protocolos)
- Gestión de infraestructura (Proxmox, VMs, redes)
- Desarrollo de herramientas y add-ons
- Aprendizaje continuo y memoria permanente

Piensa por sí mismo, actúa sin que se lo pidan (cosas seguras),
y SIEMPRE consulta antes de hacer cambios grandes.

STACK:
- Backend: Node.js + Express (CommonJS, require())
- Frontend: HTML/CSS/JS vanilla (un solo archivo)
- Modelo: Claude Sonnet 4.6 via API REST
- Streaming: SSE (Server-Sent Events) al frontend
- Persistencia: JSON en /data/
- Base Docker: Alpine Linux + Node.js
- Comunicación con HA: REST API + SUPERVISOR_TOKEN

3. BUCLE AGÉNTICO (CÓMO PIENSA JARVIS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Cuando el usuario envía un mensaje:

  ┌─────────────┐
  │  Mensaje    │
  │  del user   │
  └──────┬──────┘
         │
         ▼
  ┌─────────────────┐
  │ updateLiveCtx() │ ← Estado en tiempo real (luces, presencia, clima...)
  └──────┬──────────┘
         │
         ▼
  ┌─────────────────────────────────────────────┐
  │           BUCLE AGÉNTICO (máx 15 iter)       │
  │                                              │
  │  1. Enviar a Claude (system prompt + tools)  │
  │  2. ¿Claude pide tools? → Ejecutar TODAS     │
  │     en paralelo (Promise.all)                │
  │  3. Devolver resultados a Claude             │
  │  4. ¿stop_reason = end_turn? → FIN          │
  │     Si no → volver a paso 1                  │
  │                                              │
  └──────┬──────────────────────────────────────┘
         │
         ▼
  ┌─────────────────┐
  │ Respuesta final │ → SSE al frontend
  │ + guardar hist  │
  └─────────────────┘

PARALELISMO:
- Si Claude pide 3 tools en un turno → se ejecutan las 3 A LA VEZ
- Solo se separa en turnos cuando un resultado depende de otro
- Esto reduce latencia dramáticamente

El system prompt se construye DINÁMICAMENTE en cada request. Contiene:

  SECCIONES FIJAS:
  ├── TU CREADOR — Quién es Adrián, relación Tony Stark/Jarvis
  ├── PERSONALIDAD — Actúa primero, español siempre, humor sutil
  ├── AUTONOMÍA — Qué hace solo vs qué pregunta
  ├── EFICIENCIA — Múltiples tools a la vez, no repetir consultas
  ├── TU EXPERTICIA — Domótica + industrial + Linux + Proxmox
  ├── BASE DE CONOCIMIENTO — Cuándo y cómo guardar conocimiento
  ├── HERRAMIENTAS CUSTOM — Crear scripts cuando no existe solución
  ├── ENTORNO FÍSICO — Proxmox VM, infraestructura
  ├── CAPACIDADES — Lista de todo lo que puede hacer
  ├── LOGS Y DIAGNÓSTICO — Cómo usar logs del sistema
  ├── TELEGRAM — Cuándo y cómo notificar
  ├── PROYECTOS DEL USUARIO — Repos GitHub, análisis cruzado
  ├── EQUIPO DE AGENTES — Colaboración entre agentes IA
  ├── DASHBOARDS — Cards nativas, custom, buenas prácticas
  ├── RUTAS — Filesystem paths
  ├── AUTONOMÍA PROACTIVA — Reglas de pensamiento propio
  └── CREACIÓN DE ADD-ONS — Generar add-ons completos

  SECCIONES DINÁMICAS (cambian en cada request):
  ├── CONTEXTO ACTUAL — Fecha, hora, momento del día, sesión
  ├── ESTADO EN TIEMPO REAL — Luces, presencia, clima, alertas (60s)
  ├── INSTALACIÓN — Mapa completo del sistema (cada 2h)
  ├── MEMORIA DEL USUARIO — Preferencias guardadas
  ├── ERRORES CONOCIDOS — Para no repetirlos
  ├── LO QUE FUNCIONA — Éxitos registrados
  ├── PATRONES DETECTADOS — Automatizaciones sugeridas
  └── MEJORAS PENDIENTES — Optimizaciones identificadas

6. PROCESOS EN BACKGROUND
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Jarvis ejecuta estos procesos automáticamente sin intervención:

  CADA 60 SEGUNDOS:
  └── updateLiveContext()
      Consulta estados de HA y actualiza: presencia, luces, clima,
      temperaturas, media, alertas, switches

  CADA 2 MINUTOS:
  └── checkSelfUpdate()
      Refresca repos del Supervisor → comprueba si hay nueva versión
      → si la hay, se actualiza solo → notifica por Telegram

  CADA 5 MINUTOS:
  └── proactiveThinkingLoop()
      Analiza el estado del sistema (dispositivos caídos, errores en logs)
      → si hay issues: pide a Claude que los analice
      → Claude genera proactive_thought si algo merece atención
      → Notifica por Telegram (high/critical) o guarda para el chat

  AL ARRANCAR:
  └── scanInstallation() (si contexto >2h o no existe)
      Escanea: entidades, integraciones, add-ons, archivos, sistema
      Genera mapa completo para el system prompt

9. SISTEMA DE AUTO-UPDATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Developer (PC/Surface)         GitHub              HA + Jarvis
  ────────────────────          ──────            ─────────────────
  1. Edita código
  2. git push                → commit nuevo
                                                  3. checkSelfUpdate() (cada 2min)
                                                     → refresh repos Supervisor
                                                     → detecta nueva versión
                                                  4. POST /addons/self/update
                                                  5. Telegram: "Actualizado v3.2→v3.3"
                                                  6. Add-on se reinicia
                                                  7. Nuevo código corriendo

  TIEMPO TOTAL: <2 minutos desde el push

  ┌─────────┐     HTTP/Webhook      ┌─────────────┐
  │ JARVIS  │◄────────────────────►│  Agente B   │
  │ (HA)    │                       │  (otro repo)│

                   ┌────┴────┐
                   │ ADRIÁN  │ ← Jefe del equipo, aprueba todo
                   └─────────┘

PROTOCOLO:
1. Un agente detecta mejora para otro → proactive_thought
2. Propuesta llega a Adrián (Telegram/chat)
3. Adrián aprueba → agent_communicate envía la mejora
4. El otro agente aplica (o no)
5. NUNCA modificación directa entre agentes sin aprobación
